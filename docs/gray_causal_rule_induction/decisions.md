# Decisions

## 2026-06-04

### 决策

建立面向 Hopper 规则生成机制的独立灰因果图研究线。

### 背景

现有 SD 轻盈介入 TD-MPC2 实验已经在 300k 与接续训练中显示初步有效性。与此同时，两篇灰世界模型初稿强调，机制证据必须指向明确灰对象，且白化目标应以决策可达证书为边界。当前规则生成仍主要依赖 SD 反事实、replay 统计和 TVA 审计的分散指标，尚未形成统一的灰对象、证据准入和白化强度控制层。

### 选项

选项一为直接改造 SD 本体或派生灰 SD 子类。该方案能将区间预测内置到模型中，但会触及已验证有效的 SD 训练与在线接口，风险较高。

选项二为保持 SD 本体不变，新增灰规则证书层。该方案只读使用现有 SD、replay 与 TVA 产物，将灰因果图用于规则生成和规则筛选，风险较低，且与当前实验主线隔离。

### 结论

采用选项二。第一阶段实现 `GrayRuleCertificate` 审计层，不回写原规则库，不替换在线训练流程。

### 影响

后续规则生成将优先从“规则命中率和经验相关性”转向“灰边机制证据、动作稳定证书、价值证书和结构安全证书”。若证书层在 eval-only 或短接续中显示有效，再考虑是否派生灰 SD 子类或将区间输出内置到 SD 模型。

### 决策

继续推进保守灰证书过滤方向，暂不采用仅按教师或 v8 来源强筛选的规则库策略。

### 背景

`cycle_079` 灰规则变体在 400k checkpoint 上完成 3 episode、三种子 eval-only smoke。评估在所有模式下保持同一 TVA terminal prior，以隔离规则库差异。

### 选项

选项一为沿用原始 `confidence_active` 规则库，不引入灰证书过滤。该选项保持现状，但 smoke 中平均回报为 `355.452`，低于同 TVA 下的 `rule_off=359.080`。

选项二为使用保守灰过滤，仅退役 active 规则中证书为 `reject_or_retire` 的规则，或等价地保留 strict/value 证书 active 规则。该选项仅改变 4 条 active 规则，平均回报为 `363.974`。

选项三为仅保留教师或 v8 来源规则。该选项 active 规则大幅降至 31 条，平均回报为 `360.611`，收益弱于保守灰过滤。

选项四为教师或 v8 来源叠加证书过滤。该选项 active 规则降至 28 条，平均回报为 `353.022`，显示过度收缩风险。

### 结论

采用选项二作为下一阶段主方向。后续优先评估 `drop_reject_active`、`certified_active` 或 `strict_active` 这类保守灰过滤策略，不将来源强筛选作为默认规则生成策略。

### 影响

灰因果图当前主要用于规则生成后的证书化筛选和 prior 强度控制，而不是替换 SD 本体或重写主线训练流程。下一阶段可在 `cycle_080` 规则库上重复 eval-only 或短接续验证，并观察当前已启动的 `cycle_081` 是否受益于相邻周期规则结构。

### 决策

将后续灰规则机制验证的优先对象收窄为 `strict_active` 及其派生策略，暂不把 `drop_reject_active` 作为默认规则库策略。

### 背景

`cycle_080` 规则变体在 `cycle_081` checkpoint 上完成 3 episode、三种子 eval-only smoke。评估保持同一 `cycle_080` TVA terminal prior，以隔离规则库差异。四个模式的均值为：`rule_off=354.215`，`cycle080_original_active=351.972`，`cycle080_drop_reject_active=350.000`，`cycle080_strict_active=355.277`。

### 选项

选项一为沿用原始 `confidence_active` 规则库。该选项加载 `130` 条规则，本轮均值为 `351.972`，低于同 TVA 下的 `rule_off`。

选项二为使用 `drop_reject_active`，仅退役证书为 `reject_or_retire` 的 active 规则。该选项加载 `126` 条规则，本轮均值为 `350.000`，未复现 `cycle_079 -> cycle_080` smoke 中的正向结果。

选项三为使用 `strict_active`，仅保留 strict action 证书 active 规则。该选项加载 `125` 条规则，本轮均值为 `355.277`，相对原始 active 提升约 `+3.305`，相对 rule-off 提升约 `+1.062`。

### 结论

采用选项三作为下一阶段优先验证对象。`drop_reject_active` 保留为对照，不作为默认策略；原始 active 继续作为必要基线。

### 影响

灰因果图的下一步研究重点从“剔除少量拒绝规则是否足够”转向“严格动作证书能否形成更稳定的规则生成准入”。该判断仍基于 3 episode smoke，后续应通过更长 eval 或短接续训练验证。

### 决策

启动独立 300k 闭环训练，以 `strict_active` 灰证书变体作为在线规则 prior 的接入策略。

### 背景

原三种子主线已完成 `cycle_081` 训练并处于后处理阶段。用户要求终止该主线，并以同样训练口径接入灰因果规则机制，重新训练至 300k。此前两轮 eval-only smoke 显示，`strict_active` 在 `cycle079 -> cycle080` 与 `cycle080 -> cycle081` 中均为相对更稳妥的灰过滤候选，而 `drop_reject_active` 在第二轮未复现正向结果。

### 选项

选项一为直接修改原 `sd_retrospective_rule_induction` launcher。该方案改动面较大，且会混淆原主线与灰线实验产物。

选项二为新增灰线包装入口，复用原 launcher 的训练与后处理逻辑，只在下一 cycle 训练前将上一 cycle 的 confidence 规则库替换为灰证书 `strict_active` 变体。

### 结论

采用选项二。`cycle_001` 保持原 rich teacher 初始规则库，`cycle_002` 起使用上一 cycle 的灰证书 `strict_active` 规则库作为在线 prior。

### 影响

新实验产物写入 `results/gray_causal_rule_induction/closed_loop/`，不覆盖旧主线。该设计检验灰因果规则机制对闭环规则生成与训练过程的影响，同时保持 SD 本体、TD-MPC2 训练入口和原规则挖掘链路不变。

## 2026-06-11

### 决策

在 1M 接续闭环实验中加入有限记忆样本选择，控制进入规则生成链条的 episode 数。

### 背景

端到端 25k 墙钟时间从早期约 `7.77 h` 增至近期约 `11.00 h`。复查显示，规则条数只从约 `294` 增至 `338`，不是主要膨胀源；后处理样本数和反事实记录数增长更明显，`counterfactual_actions` 与 `replay_rule_scoring` 已成为主要耗时来源。

### 选项

选项一为继续保留全部选中样本。该方案证据覆盖最完整，但后处理成本会随训练步数继续增长，影响 1M 接续实验推进。

选项二为缩短 `summary_window_cycles`。该方案能遗忘更旧周期，但当前窗口已经只有三个周期，且单个 cycle step 内 episode 数随训练历史增长，单独缩短窗口不足以控制样本量。

选项三为在分层选择后增加 episode 数上限，保留最新且高对比的 good/bad 样本，并保留正式评估样本。

### 结论

采用选项三。当前策略设置为每个 cycle step 最多 `600` 条，总数最多 `1800` 条，正式评估来源不受删除。策略文件放置在当前 1M 实验输出根目录，仅影响后续周期，不回写旧结果。

### 影响

后续 SD、TVA、反事实生成、replay scoring 与规则效果审计将使用有界样本集。该改动预计降低后处理耗时，并使规则生成更接近“有限记忆”的灰世界假设：近期、高对比、可审计证据优先，过远或低信息量样本不再无条件保留。

### 决策

为主要规则后处理脚本加入默认多 CPU 并行。

### 背景

端到端变慢不仅来自样本量增加，也来自多个后处理脚本仍以单核方式扫描大量 episode 或 trace。当前服务器具有 `72` 个逻辑核心，继续单核运行会使 CPU 资源闲置，并使反事实生成、规则回放评分和规则效果审计成为周期尾部瓶颈。

### 选项

选项一为只控制样本量，不改并行机制。该方案改动较小，但在 1M 接续后期仍可能因为反事实 rollout 或 trace 扫描而拖慢。

选项二为默认使用全部逻辑核心。该方案吞吐最高，但可能与训练、I/O 和系统任务争用，且多个后处理脚本连续启动时风险较高。

选项三为默认使用有上限的自动并行，并允许命令行或环境变量覆盖。

### 结论

采用选项三。默认 worker 数为 `min(16, os.cpu_count())`，可通过 `SD_RETRO_WORKERS` 或 `--workers` 调整；launcher 层新增 `--postprocess-workers` 用于未来显式复现实验。

### 影响

后续周期的反事实生成、规则 replay scoring、子状态规则验证、v8 fragment mining 和规则效果审计将默认多进程执行。该设计与有限记忆策略互补：有限记忆减少样本规模，多 CPU 并行提高剩余样本处理速度。
